# 开发规则

## 防止“改烂”的固定流程

1. 每阶段使用独立分支，例如 `feature/production-stage8-orders`。
2. 先写会失败的测试，再写最小实现，最后重构。
3. 一次只实现一个可说明的功能；后端、前端、文档尽量分开提交。
4. 不修改与当前阶段无关的模块；发现原版环境问题只记录，不顺手大改。
5. 数据库变更必须能在全新库、旧库和重复启动三种情况下成功。
6. 测试只使用临时或匿名数据，禁止使用正式农场数据库。
7. 阶段验收前不合并、不打发布标签、不生成对外 EXE。

## Git 规则

- `origin` 是用户仓库：`zz526631245-eng/bambuddy`。
- `upstream` 是 Bambuddy 原项目，只允许拉取，禁止推送。
- 开工前检查工作区；不得用 `git reset --hard` 或覆盖别人的未提交修改。
- 提交信息应说明意图，例如 `feat(production): add stage 8 order accounting`。
- 回滚优先用 `git revert <提交>`；数据库同时恢复任务前备份，禁止删表。

## 界面规则

- 面向普通用户使用中文业务名称，如“产品零件清单”“打印方案”“生产订单”。
- 危险或不可逆操作必须二次确认。
- 明确提示当前动作是否会发送打印。阶段 8 的页面必须说明“仅保存草稿”。

## 文档更新规则

每次任务必须更新当前状态；只有实际改变长期决策或范围时才更新架构决策和路线图，不做无意义改写。交接文档必须与代码提交一致。
